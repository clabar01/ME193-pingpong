# ME193 Midterm — Virtual Ping-Pong

Cecilia LaBarge's ME193 robotics midterm. A virtual ball moves on the laptop screen (pygame); she hits it back with a **real paddle**. The laptop tracks where the paddle is (webcam + MediaPipe), and an accelerometer on the paddle tells it *when* she swung (Arduino UNO Q → MQTT).

## How the game works

0. **Pick your opponent (since 2026-10-12):** the first screen. Hold a blue or green minifig up to the camera (the YOLOv8 model from the door-to-door project, run only on this screen) for ~1 s, or press B / G, or say "blue" / "green". A blocky figure in that color then plays at the far end of the table (looks only; levels still set the difficulty). See "Opponent" below.
1. **Start / level select:** holding up an AprilTag starts the game (also from the GAME OVER screen, where a swing or Space plays again at the same level). Keyboard: 1/2/3 pick Beginner/Club/Pro and start, Space starts at the current level; D toggles the debug overlay. The tag ID picks the level, which sets ball speed and hit-zone size. Level (0/1/2) and reset (5) tags only act on the WAITING screen (ignored during a game). **Power-up cards (since 2026-10-12):** tag 10 SLOW-MO, tag 11 EXTRA LIFE, each once per **rally**: both come back whenever a rally ends (see Status).
2. **Paddle position:** MediaPipe Pose tracks the hand in the laptop webcam feed (wrist; if the real paddle hides it, the knuckles or the elbow + last forearm offset; holds 0.3 s, then "lost"); hand x/y, mapped through a 4-step calibration (left, right, high, low), move a translucent paddle left/right and up/down at my end of a first-person 3D table (since 2026-10-09). A target box marks where the ball will cross my hitting plane.
3. **Swing detection:** an accelerometer taped to the paddle is read by the Arduino UNO Q, which detects swings and publishes swing events over MQTT.
4. **Hit rule:** a hit counts only if **both** are true:
   - the paddle's center was inside the hit zone around the ball's crossing spot on my hitting plane at any moment from `PADDLE_LOOKBACK_S` (0.2 s) before contact up to contact. The zone is a box: left/right and up/down are checked separately with per-level tolerances (Beginner: left/right only; Club: both, loose; Pro: both, tight; wider in camera mode), **and**
   - a swing event arrived within a timing window around that moment: `SWING_WINDOW_FAST` ±0.35 s via the local broker / Space / `--no-imu`, `SWING_WINDOW_SLOW` −0.15/+0.6 s when swings come over hivemq (chosen at contact).
   Otherwise it's a miss and the rally ends.
5. **Goal & score (since 2026-10-12):** as many volleys (my hits) in a row as possible. The opponent never misses, so a rally ends only when I miss; the volley count (`streak`) is shown big at the top center and pops on each hit. **Rally ramp:** each hit makes the next ball harder: speed +`speed_ramp` (per level) per hit up to `speed_max`, the opponent aims wider (`AIM_SPREAD_*`), hit tolerances shrink with speed (`ZONE_*`, floor 60%); all back to the level's start values after a miss. The AprilTag level sets the starting speed and ramp. Passing the record (≥ 3) shows "HIGH SCORE!" with the bell chime. When the all-time record is beaten, publish it (see MQTT below).
6. **LED matrix:** the UNO Q's LED matrix shows the ball as a single dot, mirroring the on-screen ball.
7. **Sounds:** pyAudio (`laptop/sounds.py`), rules in "Sound rules" below.
8. **New feature (not done in class): voice commands with Vosk** (chosen 2026-10-12, Phase 9). Offline speech recognition: "smash" (voice power-up), "play again", "level one/two/three", "pause"/"resume", "score" (spoken with pyttsx3). See "Voice commands" below.

## MQTT topics

| Topic | Direction | Content |
|---|---|---|
| `ME193/Rogers/CeciLaBarge` | laptop → broker | **Only** the record number of continuous hits, as a **float** (e.g. `12.0`), **retained**, published **every time the record changes**. Nothing else is ever published here — no debug, no state, no strings. |
| `ME193/CeciLaBarge/imu` | UNO Q → laptop | Swing events from the accelerometer |
| `ME193/CeciLaBarge/game` | laptop → UNO Q | Ball position + game state for the LED matrix dot |
| `ME193/CeciLaBarge/imu/rejected` | UNO Q → laptop | Moves that failed the swing checks: never a hit, but the game shows them as the miss reason "SWING REJECTED (…)" |
| `ME193/CeciLaBarge/imu/raw` | UNO Q → laptop | Only with `DEBUG = True` on the board: raw samples for labeling |

Broker address, topics, and credentials are configured in `config.py` / `board_secrets.py` — never hard-coded elsewhere.

**Brokers (since 2026-10-11):** the record topic `ME193/Rogers/CeciLaBarge` is always on **broker.hivemq.com**. The fast topics (`ME193/CeciLaBarge/imu`, `.../imu/rejected`, `.../game`) go through a **local Mosquitto broker on the UNO Q** (`~/ArduinoApps/local_broker`, Docker container `me193-mqtt`, port 1883, `--restart unless-stopped`), which **bridges `ME193/CeciLaBarge/#` both ways to hivemq** (MQTT v5 bridge; tested: each message exactly once on each side, no loop). Laptop: `GameMqtt` connects to `<BOARD_IP>:1883` (from `~/ArduinoApps/tools/board_secrets.py` via `laptop/board_settings.py`; `config.LOCAL_BROKER_*`) plus hivemq; publishes game state on local while connected, else hivemq; takes swings/rejected moves from both and drops the bridge duplicate by `(topic, t, peak)`. paddle_imu: connects to `msgpack-rpc-router:1883` (the board itself, from inside the container) plus hivemq; publishes on local while up, else hivemq. Screen shows `IMU/game via local <ip>` or `via hivemq (local down)`. **Measured on 29BCNet (2026-10-11): swing board→laptop via local median 20 ms (4–133), via hivemq median 2057 ms (729–4054)**; clock offset board−laptop +58 ms. Fallback via the bridge works but takes 1.6–4 s on that network. Restart the broker: `python3 tools/deploy.py --cmd "sh /home/arduino/ArduinoApps/local_broker/start_broker.sh"`.
**Connection health (since 2026-10-11, session 3):** the laptop's local client uses keepalive `LOCAL_KEEPALIVE_S` = 5 s and pings itself through each broker every second on `ME193/ping/CeciLaBarge-<id>` (outside the bridged `ME193/CeciLaBarge/#`); local counts as down if paho is disconnected OR no echo for 2.5 s → game state + swing window switch to hivemq. paho reconnects by itself; every drop is printed with time + reason and listed (with downtime and the measured swing delays / ping round trips) in the summary at quit. paho quirk: a socket error inside `select()` reconnects WITHOUT calling `on_disconnect`, so a connect while already "connected" is also logged as a drop. **"Unspecified error" = connection lost.** The drop in session 2 was the **board losing power**: `journalctl --list-boots` showed 6 boots within seconds, each ending abruptly mid-boot (brown-out loop), and the board vanished from the network again at 18:21 the same evening. The board has no RTC, so boot timestamps before NTP sync are wrong. Check power (cable / battery on the paddle) before blaming MQTT. `tools/imu_logger.py` defaults to the local broker (`--broker hivemq` to compare).

## Rules for working on this project

- **Python on the laptop.** (UNO Q side uses whatever the board needs — Arduino sketch and/or its Python app.)
- **All tunable values live in one `config.py`:** thresholds, timing window, ball speeds, hit-zone sizes per level, AprilTag ID → level map, MQTT broker/port/topics, camera index, screen size, etc. No magic numbers scattered in other files.
- **Threads:** camera (MediaPipe + AprilTag), MQTT, and audio each run in **their own thread** so the pygame loop never blocks. Threads share state through thread-safe structures (locks / queues / latest-value holders); the game loop only reads the latest values.
- **Keyboard fallback always works:** a keyboard paddle mode (arrow keys move the paddle, Space = swing while playing) must remain available so the game is playable/demoable with no camera or no UNO Q (`--no-imu` makes every ball count as swung).
- **Never commit secrets:** `board_secrets.py` and any API keys (e.g. LLM / TTS keys) must be in `.gitignore`. Provide a `board_secrets_example.py` template with placeholder values instead.
- **Explain the logic in comments:** the hit rule and the swing-detection logic must have clear, plain-language comments (what is checked, why, which config values control it) — Cecilia quotes these in her write-up.
- **After every step, give exact testing instructions:** commands to run, what to do physically (e.g. "hold tag 3 up to the camera"), and what she should see/hear if it works.
- Build in small steps; don't write code beyond the current step.

- **IMU (`~/ArduinoApps/paddle_imu`, step 1 done 2026-10-09):** MPU6050 (GY-521) on the header SDA/SCL = `Wire` (i2c2), address 0x68, WHO_AM_I 0x68 (genuine). UNO Q buses: `Wire`=i2c2 header, `Wire1`=i2c4 Qwiic, `Wire2`=i2c3 A4/A5. Read in the **sketch** (raw registers, no library) at 100 Hz, ±8 g, ±2000 °/s, DLPF 44 Hz; each sample goes to Python with `Bridge.notify("imu_sample", t_ms, ax, ay, az, gx, gy, gz)`; status/I2C scan via `Bridge.notify("imu_status", text)`. Python logs every 10th sample. At rest |a| ≈ 0.97 g, gyro bias ≈ 1–2 °/s. `arduino-app-cli app logs <app>` shows only the last 100 lines; use `--tail 100000` to see startup messages.
- **Swing events (paddle_imu, deployed 2026-10-09):** detection in `paddle_imu/python/swing_detector.py` (pure Python, unit-tested on laptop): candidate when |a| − 1 g > 2.0 g; swing only if peak accel ≥ 2.2 g **and** peak gyro ≥ 500 °/s (gyro from 100 ms before the start); decided ≤ 60 ms after the start; 300 ms refractory after an accepted swing. See "Swing threshold tuning". One MQTT message per swing to `ME193/CeciLaBarge/imu`, QoS 0: `{"swing": 1, "peak": <g>, "unit": "g", "peak_gyro": <°/s>, "t": <swing start, Unix s, board clock>}`; rejected candidates (`"swing": 0` + `"failed"`) go to `ME193/CeciLaBarge/imu/rejected`. `DEBUG = False` (True: per-sample CSV on the board + raw stream to `.../imu/raw`). Laptop: `python tools/imu_logger.py` prints swings and rejected moves.
- **After moving the board to another WiFi, restart the app container.** A running app keeps the old network's DNS (seen 2026-10-11: container still had `search tufts.edu`; DNS failed inside it, MQTT stayed DISCONNECTED while the board itself could reach the broker). Fix: `arduino-app-cli app stop <app>; docker rm <app>-main-1; arduino-app-cli app start <app>` (a reboot also works). Check with the `status:` log line (`MQTT connected`).

(cooldown)). Not-done commands are also logged (`VOICE '...' not done: ...`). - **pyttsx3 on macOS only speaks from a process's main thread** (in a thread `runAndWait()` returns at once, silent; in the game's main thread it blocks ~2.4 s), so `speech.py` runs it in a helper process (`python laptop/speech.py --serve`, lines on stdin, "start"/"done" on stdout); `say()` returns in ~0.1 ms. Falls back to the macOS `say` command if pyttsx3 can't start.
- **"blue" / "green" (2026-10-12):** pick the opponent on the select screen, switch it on WAITING / GAME OVER, "<color>: not now" otherwise. Not strict (a wrong pick costs nothing). Measured like above (4 voices): 8/8 clean, 6/8 at 10 dB, 0 false triggers on sentences that mention both colors ("green [unk]" is ignored).
- **Write-up, 2 sentences:** Vosk is an offline speech recognizer (built on the Kaldi toolkit): a small neural acoustic model turns each 10 ms slice of microphone audio into probabilities of speech sounds, and a decoder searches a pronunciation dictionary and language model for the word sequence that best explains those sounds. We restrict the decoder to a tiny grammar of only our ten commands plus "unknown", which makes it fast and robust on a laptop CPU, and we double-check the disruptive commands with a second, unrestricted recognizer so that similar-sounding phrases are rejected.

Why not ultralytics in this venv: it pulls torch and `opencv-python`, which must never sit next to `opencv-contrib-python`. **Checked: on the dataset's 9 test + 6 validation photos, OpenCV gives the same classes and confidences (2 decimals) as ultralytics with best.pt;** ~23-41 ms per frame on the laptop CPU. `MinifigProcessor` is a camera processor that runs only while `.active` is set (select screen), at most `MINIFIG_HZ` 8 times/s, `MINIFIG_CONF` 0.5 (as in detect_live.py); during play it returns at once. `OpponentPicker`: the same color for `MINIFIG_HOLD_S` 1.0 s, gaps up to `MINIFIG_GAP_S` 0.35 s forgiven, a color switch restarts the hold, both in view → the more confident one.
- **Figure (`opponent.py`, cosmetic only: reads the game, never writes it; game_state.py doesn't know it):** original blocky toy figure (square head with eyes + mouth, box body with a white stripe, box arms/legs, mitten hands, paddle; no logos), every part a shaded 3D box drawn far-to-near in the game's perspective (`Projection` = view3d's formulas). Blue: calm idle, smaller swings (`amp` 0.9), flat dark cap, nods when I miss. Green: bouncy idle, bigger wind-ups (`amp` 1.3), spiky hair, grin, jumps with arms up when I miss. The legs are behind the table in play (like a real player); they show on the select screen.
- **Motion:** a pose = 15 joints relative to the hip center in table axes; clips: idle (loop), sidestep (leg cycle, phase advances with the distance slid), forehand / backhand (takes with a contact frame). Retargeting keeps each bone's direction and uses the figure's bone lengths (`BONES`). States: idle sway → the body follows the Opponent AI's paddle x (smoothed; legs step in proportion to the speed) → **swing timed from the ball**: time to contact = (OPP_HIT_Z − ball z) / ball vz every frame (so slow-mo slows the swing too); forehand if the ball arrives on the paddle-hand side (> −8 cm), else backhand; the stroke blends in before its wind-up, plays its contact frame exactly on the frame the game returns the ball (`opp_hit`; serves: GO), then follows through; over the last 0.4 s the arm is nudged so the paddle center lands on the predicted crossing spot (`predict_crossing_xy`, computed once per shot). Reaction on my miss (`life_offer` / `game_over`). Paused: frozen.
- **Recording your moves (`tools/record_swing.py`; not record_swings.py, the IMU tool):** guided idle (4 s), forehand (9 s, 3-4 swings), backhand (9 s), sidestep (6 s) with MediaPipe world landmarks → `assets/motions/<name>.json`. Each swing is found by the paddle hand's sideways speed in the stroke's direction (right-handed forehand → +x, backhand → −x; so the backswing doesn't count), peaks ≥ `SWING_MIN_SPEED` 1 m/s and ≥ half the fastest, ≥ 0.8 s apart; contact = the middle of the fastest part (frames ≥ 80% of the peak within 0.25 s); 0.6 s before / 0.5 s after kept. Idle/sidestep: 2.4 s from the middle, end crossfaded into start. 30 fps, 3-frame smoothing, gaps interpolated. `--view` plays them on both figures, `--clear` deletes them, `--hand left`. Missing / broken files → procedural (message).
- **Measured (2026-10-12):** the paddle center meets the ball at every return: max 0.46-0.77 cm over 25-volley rallies × 3 levels × both figures × slow-mo on/off (the rest is the game's one physics step at the opponent's plane), serves 0.00 cm; with recorded clips (synthetic recording test) 0.45 cm. Synthetic recording: 3 of 3 swings found, contact within 1.3 frames, idle loop seam 0.4 cm. **Cost:** posing 0.06 ms median (max 0.6) per frame; whole frame 2.7 ms with the figure vs 1.8 ms without (3600 frames, budget 16.7 ms at 60 fps); in the real game loop 0.14 ms median. **Timing unaffected:** a seeded 3600-frame game gives the identical trace (every event, state, volley count and ball position to 1e-9 m) with and without the figure. YOLO costs nothing during play (inactive).

## Swing threshold tuning (2026-10-09, for the write-up)

**Round 1: acceleration only** (hand test with `tools/imu_logger.py`, detector at a 1.5 g placeholder). Real swings peaked at **1.5–5.2 g** (|a| − 1 g), most 2–4 g, about a quarter under 2.1 g. Fake moves (sliding, reaching, wiggling) peaked at **1.51, 1.62 and 2.11 g**. The ranges overlap, so no acceleration threshold separates them. Interim choice 2.0 g (rejected 2 of 3 fakes, cost: the weakest swings).

**Round 2: acceleration + rotation (gyro)** — raw output in `data/gyro_test.txt`. Every move above 2.0 g was reported with its peak accel and peak gyro (gyro peak counted from 100 ms before the start); #1–10 real swings, #11–15 fakes (sliding/reaching).

- **Neither signal alone works:** swings 2.56–5.79 g vs fakes 2.10–2.82 g overlap in acceleration; swings 540–934 °/s vs fakes 184–577 °/s overlap in rotation.
- **Both together do:** a swing must have peak accel ≥ **2.2 g** AND peak gyro ≥ **500 °/s**. All 10 swings pass both checks; **each fake fails at least one**: the hard-but-not-turning moves (#11, #14) fail the gyro check, the turning-but-gentle ones (#12, #13) fail the accel check, #15 fails both. Physically: a real stroke is both a hard acceleration and a fast wrist rotation; sliding or reaching the paddle around is usually only one of the two.
- **Implementation** (`paddle_imu`, settings at the top of `main.py`): a candidate starts at 2.0 g (same as when the data was measured, so peaks are measured the same way), peaks are taken over ≤ 60 ms (gyro from 100 ms before), then both checks. 300 ms refractory only after an accepted swing. Rejected candidates go to `ME193/CeciLaBarge/imu/rejected` (tuning only; the game listens to `.../imu` alone).
- **Caveat — small sample, tight margins:** only 15 labeled moves, one session, one person. Several fakes are rejected by a single check and only just: #13 by 0.06 g, #12 by 0.10 g, #11 by 23 °/s; the closest real swings clear the thresholds by 0.36 g (#5) and 40 °/s (#6). **Needs a retest on the real paddle** (sensor mounted as in play, real returns, more fakes) before calling it final; expect the thresholds to move.
- **Why occasional false triggers are acceptable anyway:** a swing event alone never scores. The hit rule requires the paddle (wrist, from the camera) to be in the hit zone **and** a swing within the timing window around the moment the ball reaches the paddle. A fake trigger at any other time is ignored; it only matters inside that short window while the paddle is already in the right place, which is rare. Missed real swings are the costlier error.

## Record rules (ME193/Rogers/CeciLaBarge) — decided by Cecilia 2026-10-08

1. **Load first.** On connect, subscribe to the score topic and read the retained value = all-time record; `best_streak` starts from it (or stays higher if this session already beat it). **Nothing is published on the score topic until the record has loaded** (no retained value within `RECORD_LOAD_WAIT_S` = 2 s after SUBACK → topic counts as empty).
2. **Topic always matches the game's record.** After loading, whenever `best_streak` ≠ the broker's value, publish `str(float(best_streak))`, QoS 1, retained: beating the record (up) **and tag-5 resets (down)**. A tag-5 reset before the record loaded wins over the loaded value. Re-sent after a reconnect if never confirmed. Payload is only the float; nothing else ever goes on this topic.
3. **Only real play publishes.** `publish_score = --input camera AND IMU active (MQTT on, no --no-imu) AND not --no-publish` (updated 2026-10-09, Prompt 6). Keyboard, `--tags` and `--no-imu` modes connect, load and show the record but never publish to the score topic. `--no-publish` blocks score publishing in any mode (game topic still sent). In camera mode only real IMU swings count (no Space swing), so a published record always comes from real paddle swings.
4. Tools: `python tools/watch_score.py` (print every update, flags non-floats), `python tools/clear_score.py` (shows the retained value, asks to type "clear", then publishes an empty retained message). Both take `--topic` for test topics.
5. **Testing rule: never let tests reach the real score topic.** Test harnesses must set `config.MQTT_ENABLED = False` or point `SCORE_TOPIC` at `ME193/CeciLaBarge/test-<random>/...` (and clear retained test values afterwards). A test run on 2026-10-08 accidentally left a retained `1.0` on the real topic (old code published from keyboard/--tags mode).
